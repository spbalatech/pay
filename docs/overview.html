Aegis

A closed-loop chargeback defense agent for PayPal merchants. It prevents disputes before they are filed, defends the ones that land, and turns every outcome into a prevention rule — so the same loss does not happen twice.

Stack Next.js 14 · TypeScript · Postgres · Prisma PayPal 10 API families + webhooks Model Claude or local Llama License MIT

01Run it

Five commands from a clean clone. Only DATABASE_URL is actually required — everything else degrades in a named way rather than failing.

Prerequisites

  • Node 18 or newer
  • Docker, for Postgres — or any Postgres 14+ you already have
  • Optional: a PayPal sandbox app, for live writes
  • Optional: an Anthropic API key or a local Ollama, for the drafting and rule-writing agents

Start

# from the repo root
npm install
cp .env.example .env

docker compose up -d          # Postgres on :55439
npx prisma migrate deploy     # create the schema

npm run seed                  # 90 days of merchant history
npm run agents:run            # one full pass of the loop
npm run dev                   # console on :3000
No PayPal account yet? npm run seed -- --offline builds the whole history without calling PayPal. Three of the four agents still run to completion, because their scores are arithmetic rather than model output.

Diagnostics

npm run ai:check              # which model provider is live, with a round trip
npm run paypal:check          # exercises all 10 PayPal endpoints Aegis uses
npm run webhook -- list       # registered webhook subscriptions

Choosing a model

Set AEGIS_AI_PROVIDER to anthropic, ollama, none, or auto — which prefers a configured Anthropic key and falls back to a reachable local Ollama. Nothing else changes; both providers sit behind one interface and the agents never know which is in use. 

# hosted
ANTHROPIC_API_KEY=sk-ant-…

# or entirely local, no API key, no network
AEGIS_AI_PROVIDER=ollama
OLLAMA_MODEL=llama3.1:8b

Demonstrating the webhook path

PayPal has to reach the endpoint from the public internet, so put a tunnel in front of it. 

npm run dev
cloudflared tunnel --url http://localhost:3000     # second terminal

npm run webhook -- register https://<tunnel>/api/webhooks/paypal
# put the returned id in .env as PAYPAL_WEBHOOK_ID, then restart

curl localhost:3000/api/webhooks/paypal            # liveness + event counts
Do not set AEGIS_WEBHOOK_ALLOW_UNVERIFIED in a demo anyone can reach. It exists so the handler can be exercised against PayPal's simulate-event endpoint, whose events can never pass real signature verification. Unset means off, which is the right answer everywhere else.

Hosting it

One Next.js service plus a managed Postgres. Set DATABASE_URL and the PayPal credentials as environment variables, never in the repo; build with npm run build, which runs prisma migrate deploy first. Then register the webhook against the deployed URL instead of a tunnel.

03Architecture

Four agents around one loop. The arrow from Learner back to Sentinel is the product; the rest is plumbing.

Why the scores are not written by a model

Risk scores and expected values are plain arithmetic over facts the system can point at. The model's jobs are the ones language is good at: explaining which signals fired, drafting buyer outreach, writing rebuttals, proposing rules. It never invents a number.

That split is what lets a merchant ask why did you hold my order? and get a list of weighted signals instead of a vibe — and it means the same inputs produce the same score on every run.

04Flow

One order, through all four agents. The dispute that never happens is the cheapest one.

Defend

Deadlines stop being how you lose

Cases are lost by default because assembling evidence from four places takes 40 minutes nobody has. Every dispute is triaged the day it lands.

Defend

You stop losing money by winning

On a $68 claim with weak evidence, fighting costs $94 and accepting costs $70. The agent says accept, and shows the arithmetic.

Prevent

Most chargebacks are not fraud

A parcel that stopped moving, a forgotten subscription, a duplicate charge. A fraud score at checkout is blind to all of it; a lifecycle agent is not.

Prevent

Intervene inside the window

There is a period where the buyer is annoyed at the merchant and has not yet called their bank. That is the cheapest dispute prevention available.

Learn

It compounds

Month one it defends. Month six it has rules that permanently closed three classes of loss, each traceable to the disputes that justified it.

Learn

You can always answer “why?”

Weighted signals and a dollar figure, with every agent action and human override in an audit log grouped by actor.

What it is not

PayPal's risk engineAegis
Scores fraud at authorizationWatches the whole lifecycle, after payment
Generic across all merchantsLearns this merchant's reason codes from this merchant's outcomes
Catches stolen cardsCatches service failures and friendly fraud — the majority
Produces a scoreTakes actions under the merchant's own ceilings, with an audit trail

Where the merchant stays in charge

Auto-accept ships disabled. PayPal's own integration guidance is that a dispute claim should never be accepted automatically without review, so a merchant has to opt in by setting a ceiling. With it off the Advocate still assembles the evidence, computes the expected value and drafts the rebuttal — and a human presses the button. The agent removes the 40 minutes of assembly, not the decision.

07About the demo data

Two things the PayPal sandbox cannot originate. Aegis does not pretend otherwise, and every row carries its provenance.

MarkerMeaning
LIVE_SANDBOX Created at PayPal and fully real — catalog products, subscription plans, invoices created and sent, and any dispute arriving through the webhook
LIVE_UNCAPTURED The order genuinely exists at PayPal and is fetchable by id, but capture needs browser approval or Advanced Card Payments on the business account, so the capture id is local. The order is real and the payment is real are different claims
SIMULATED A fixture. Inbound buyer disputes cannot be filed against a sandbox merchant at all, so the seeded dispute history is written directly to the database

The console badges simulated rows, the seeder prints the split on every run, and every action an agent takes runs against the live sandbox API. A refund against a simulated order records as skipped rather than being faked against a capture id that does not exist at PayPal.

The seeder also plants one recurring loss shape on purpose — high-value orders to multi-unit addresses shipped without signature confirmation — so the Learner has a genuine pattern to find rather than noise.
